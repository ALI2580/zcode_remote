# ZcodeRemote 性能优化专项：长程执行 Prompt

请在当前 ZcodeRemote 仓库执行性能优化专项，持续完成“可复现基线 → 定位 → 实现 → 前后对照 → 行为回归 → 证据归档”。这是实施任务，不能只交分析或建议。中文沟通。

## 1. 启动与范围

先读 `.agents/skills/project-cognition/SKILL.md`、其 development-rules / release-and-testing，以及 `references/optimization-code-audit-2026-09-14.md`。再核对最新 `ui-parity-current-todolist.md`、实际 HEAD、dirty diff、工具链与设备条件。审计中的行号/规模/测试结果只是历史起点，重新定位符号。

范围：聊天流式更新和长历史、滚动阅读与搜索定位、代码/Markdown/diff、来源/会话切换、设置读取、语音及模型处理、必要的平台内存与生命周期验证。优先优化已测出的瓶颈；不扩展成 UI 重设计、协议重写或新功能项目。

保存既有改动清单与涉及文件快照/哈希，保留已有未提交工作。已知聊天/渲染/外壳文件可能有其他任务修改。发现同时修改时重新读 diff，缩小本批文件范围；不要直接 reset、覆盖或全仓格式化。

## 2. 建立可比较基线（P0）

建立 `references/optimization/performance-todolist.md` 和 `build/optimization/<唯一批次>/`；若已存在则接续，不覆盖旧证据。记录源码身份（HEAD+dirty 文件哈希）、模式、设备型号/ABI/OS、刷新率、逻辑分辨率、Flutter/Dart、fixture 版本、采样步骤和原始数据。

建立确定性合成场景，建议梯度是负载范围，不是已经验证的容量承诺：

| 场景 | 负载 | 指标 |
| --- | --- | --- |
| 长对话流式更新 | 1k/5k/20k 行，固定内容与追加序列，10/30/60 个 delta 每秒 | applyFrame/行更新、分组耗时与调用数、分配、通知与实际 build 次数、输入响应 |
| 阅读与历史 | prepend、折叠、A→B→A、宽度/字号变化、搜索旧片段 | 锚点误差、定位延迟、帧耗时、分页/RPC 数 |
| 代码与 diff | 100/1k/10k 行，超长单行、中文、深浅主题、流式追加 | 解析/布局耗时、UI/raster p50/p95/p99、超预算帧比例、峰值内存 |
| 来源与设置 | 假服务多来源切换，20 次 warm-up 后至少 100 次切换循环 | 重复读取、活动订阅/计时器数、稳定后内存趋势、取消与迟到结果 |
| 语音/模型 | 已有 cold/warm/preview/cancel 入口 | 模型加载、识别、UI 阻塞间隔、取消延迟、音频复制与解压峰值内存 |

先用最小可运行数据校验工具，再拓展梯度。基线与优化后使用同一 fixture、同设备/模式、同采样条件。算法基准预热后至少 5 轮；设备场景至少 3 轮，报告离散程度和样本量。短样本不要过度解读 p99，需报告采样帧数；冷启动与暖路径分别统计。

CPU 微基准与设备流畅度分开：纯 Dart 基准能说明算法路径，widget/debug 测试能说明行为；实际流畅度以支持 profile 的目标设备为准。记录 UI/raster 各自耗时，不盲目相加当帧时长。60Hz 可用 16.67ms、120Hz 可用 8.33ms 作为各阶段参考预算，按实际设备刷新率换算，不能把 60Hz 结果当 120Hz 达标。

没有合适设备时继续基准、回归和确定性计数，明确设备性能待验证。已有语音 FrameTiming 入口需复用。不得把 debug 模拟器结果作为 release/profile 真机达标证明。

## 3. 按收益执行候选

- P1：测 `ConversationState._applyDelta` 的 rowId 线性查找；确有收益时引入受控索引，并验证 snapshot、upsert、remove、prepend、epoch、unknown ID、恢复的索引一致性。
- P2：测 `ChatPage._onState` → `_buildChat` → `conversationTurnGroups`，以及 `ConversationViewport` 锚点扫描。可按修订号/结构变更类型更新投影，缩小 rebuild；rows 可原位变化，禁止仅以 List identity 失效缓存。
- P3：测 `CodeSyntaxHighlighter`、代码与 diff 组件；只对测得的重复解析/布局优化。缓存必须可失效且有界，不无限保留文本/AST/Spans；保持长行、复制、选择、行号、字体缩放、主题和辅助功能。
- P4：测 WorkspaceShell 的来源页面保留、隐藏监听和设置刷新；缩小通知范围、正确来源内去重读请求、释放无用资源。每来源当前页面保留与每任务缓存是不同语义，先查源码再判断。
- P5：复测已使用 isolate 的语音和模型解压；仅在证据支持时优化传递、预览调度、峰值内存。必要时扩展终端吞吐/RPC 分片/恢复写入测量，不预设它们是瓶颈。

每批一个主要假设、一个可独立回滚的修改，先记录原始基准，再实现，再复测同场景。结构耦合阻碍修改时仅做最小必要提取，并登记给结构专项；不要同时重构整个模块。

## 4. 行为约束与验收

保持纯 Dart 协议边界、全部官方字段/门控；bridge 新代次 Initialize 后恢复订阅；旧代次/旧来源结果丢弃；首发与已受理写操作不自动重发。设备/transport、workspace、session、provider/org/project、logEpoch 分开，不能为了缓存命中而省略作用域。

通知合并只允许作用于派生显示更新，不能吞掉协议事件、审批/控制态变化或写入确认。保持阅读锚点、真实滚动决定跟随、草稿/附件、输入法和连续交互。

基线建立后、实施前，给每个候选登记主指标、绝对目标、相对目标及非退化指标；默认以主指标改善至少 15% 且超过重复测量噪声作为保留性能修改的参考，非目标路径若回退超过 5% 需解释并修正或撤回。百分比只是初始决策规则：本就很快的路径优先证明复杂度/分配收益与绝对耗时，禁止通过事后改阈值包装成功。

每个保留的性能修改至少提供一项可量化收益及行为回归。未发现值得保留的收益时可以关闭该候选，附完整测量依据；不得为凑优化数量保留复杂代码。设备未测项不能标记性能达标。

测试先最短相关集合，再阶段完整 analyze/test/smoke；新增测试应验证真实失败、复杂度或契约。确定性操作次数可用于 CI，易抖动的绝对毫秒不要硬塞普通单元测试。Kotlin/Gradle 改动实际编译 Android。同工作区 Flutter/Gradle 验证串行。

## 5. 长程接续与完成

首轮完成一个可复现基准和首个候选验证；已有可靠基线则直接进入一个实现批次。不能只建清单结束实施。每批更新条目状态、改动、原始/优化数据、回归命令及退出码、剩余条件和下一条可执行命令。

持续执行已授权的本地工作，不因一个设备/官方对照条件缺失而停止独立项，也不循环重复同样失败。中断/上下文切换前保存当前进行中修改和接续入口；恢复后从未完成项继续，不重做已经有效的检查。

完成条件：P0–P5 全部有判定（已验证优化/测量排除/条件受阻），所有已保留修改有基准收益和行为回归，适用静态分析/测试/smoke 通过，目标设备验证到位。必需设备验收受阻时只报告本地阶段完成，不宣布专项全部完成，更不能关闭产品 UI parity 总目标。

真实远端默认只读，写操作用合成服务，凭据仅运行时注入。产品包与 QA 包严格区分。提交、推送、发布、真实写操作按现有明确授权执行，不由本 prompt 自动扩张范围。最终交付真实数据、改动文件、验证结果与尚未满足条件。
