# ZcodeRemote 重建审查与实施规格

审查日期：2026-09-08。状态：方案与现状基线，尚未实施架构迁移。

**路线已更新：纯 Flutter Android 应用。** 下面的 Web 宿主建议和 M0 记录仅为历史方案；最新实施状态见 [flutter-android-integration.md](flutter-android-integration.md)。不再交付独立 Web 版，也不在应用内嵌 WebView 承载主界面。

设计更新：已认可的后续需求与第二版交互草稿见 [design-draft-v2.md](design-draft-v2.md)。聊天 header 保留官方任务栏；设备切换改在左侧导航底部；主题移入设置中心。以下初稿对应设计位置以 V2 为准。

实施更新：已新增 [Web 运行验证版](../web_client/README.md)，直接加载官方资源并验证多设备页面与 Web Storage 隔离。M0 的真实配对及视觉验收仍待完成，尚未进入 Android 主入口迁移。

## 1. 产品目标

- Android 手机/平板为主要使用端，同时保留浏览器 Web。
- 进入某台设备后，以 ZCode 官方远程网页的 UI 和行为作为验收基准。
- 多设备是客户端增加的能力：独立连接、切换、恢复、凭据管理，以及每台设备自己的工作区、任务、草稿和阅读位置。
- 设备入口属于新增设计范围，使用官方视觉语言；不能称为官方不存在页面的「1:1 复刻」。

「1:1」必须绑定具体 Web 构建、相同数据、语言、主题、字体、容器尺寸和交互状态。截图相似不能代替行为验证，单元测试通过也不能证明功能齐全。

### 2.3 已确认缺陷

以下是审查发现，**尚未修复**。

1. **正式版缺联网权限**：`android/app/src/main/AndroidManifest.xml` 没有 `INTERNET`；现有 release 合并清单也没有，只有 debug/profile 声明。远程连接需要该权限，能启动空页面不能证明 release 可联网。
2. **Android 凭据加密未接通**：`CredentialCipher` 调用 `zcode_remote/crypto`，但 `MainActivity` 只有空 `FlutterActivity`，没有处理器。异常被捕获后回退到明文，README 的 Keystore 存储说明与实现不符；主清单也未禁备份。
3. **加密成功后反而不能解析**：`DeviceStore.addUrl()` 把密文放进运行时 `Device.url`，`Device.params` 却直接解析它；`load()` 没有解密流程。需分开内存凭据与落盘序列化，覆盖失败与迁移路径。
4. **更新链接不更新凭据**：同 sid 再导入只修改名称与时间，保留旧 URL；更换配对凭据后仍可能使用旧值。
5. **「已连接」是静态文案**：设备卡恒定显示绿点与已连接，未读取真实连接状态；`DeviceSession.connected` 也仅判断 client 非空。
6. **切设备等于拆连接**：`WorkspacePage.initState()` 创建连接，`dispose()` 断开连接。返回选另一台设备不能保留上一台会话运行时。
7. **异步连接生命周期缺口**：连接成功前的局部 client 没有由失败清理路径可靠释放；多次连接没有共用 pending Future；页面销毁后 await 续体仍可能赋值、通知。需要 generation/cancellation 防护和故障注入测试。
8. **已有任务入口缺失**：工作区页面直接创建 `ChatPage`，未传 sessionId；UI 未接 `subscribeSessionsIndex`/`listTasks`，协议能力存在但导航未使用。
9. **composer 不是完整实现**：只有文本框和发送；没有模型/模式/思考/@引用等。`canSend` 只在 build 时读取 controller，缺少输入监听驱动重建，输入后按钮可能仍禁用。首次发送也没有采用已记录的 `createSession(firstInput)` 普通文本路径。
10. **正文与恢复未闭环**：assistant 用 `SelectableText`，无 Markdown 渲染；页面没有完整历史分页、用户滚动跟随状态机、bridge recovered 后重新获取 transport/订阅与持久草稿。
11. **设备身份不稳定**：以 sid 作为本地记录 id，把配对会话身份与设备身份混在一起，也没有明确 origin 作用域。重建中以本地 UUID 做主键；origin+mid 只在确认服务端语义后用于辅助识别，凭据轮换不丢本地记录。
12. **视觉参考混用**：主题 primary 仍用紫色/橙色，首页大量蓝紫装饰；部分图标/弹窗写死浅色或深色令牌。历史文档对模式图标、断点、重连次数等有矛盾，需用当前源码与截图逐项解决。

## 3. 路线决策

建议优先验证 **Web 为核心的界面 + Android 宿主**，把两端的界面和交互尽可能落在同一份 Web 实现上。Android 宿主承担 Keystore、键盘/系统返回、文件选择、通知和更新等平台能力。已有 Flutter 工程可在验证阶段继续做宿主，是否移除 Flutter 留到端到端验证后决定。

这是基于目标的工程建议，**不是已证明可以直接复用整套官方生产 bundle 的结论**。

| 路线 | 优点 | 代价与关键未知 | 结论 |
| --- | --- | --- | --- |
| Flutter 逐组件重写 | 协议 Dart 可直接复用，原生平台能力易延续 | Web 的编辑器、排版、选择、弹层、滚动和动画都需维护第二份行为 | 可实现，但当前工程尚无支撑严格对齐的完整规格和验收体系 |
| 官方远程网页直接放入 WebView | 单设备能使用官方原始界面与行为 | 依赖在线版本；多页面同源存储、iframe 限制、宿主回调和后台状态均需验证 | 适合先做可行性验证，不能等同完整多设备产品 |
| 自有 Web 界面与行为实现 + 宿主 | Android/Web 共用 DOM/CSS 与组件，设备作用域可控 | 若无法取得可维护源码，仍需完整重建协议适配和组件，工作量不会凭空消失 | 长期优先方向，按实际资源验证结果决定复用边界 |

**不以修改压缩 JS 中的混淆函数名作为长期架构。** 生产资源完整性、版本固定、依赖加载、协议入口以及多设备隔离都必须先验证。保留原项目和测试作为对照，验证成功后再迁移主入口。

若 Web 复用验证不成立，回到 Flutter 路线时也必须采用下面的统一状态作用域、功能矩阵与视觉验收，不能继续逐处凭印象修图标。

平台依据：Android 官方支持通过 [WebView 承载网页及接入宿主能力](https://developer.android.com/develop/ui/views/layout/webapps/webview)；同源页面的 localStorage 共享、sessionStorage 按标签页和 origin 分区，详见 [Web Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API)。因此「每设备开一个网页对象」本身不能证明存储已隔离。

## 4. 多设备核心契约

```text
AppController
  ├─ DeviceRegistry                         持久化记录、名称、凭据版本
  ├─ DeviceSessionManager
  │    ├─ device A → DeviceRuntime
  │    │    ├─ Relay/Bridge 与重连状态机
  │    │    ├─ WorkspaceRuntime[workspaceId]
  │    │    │    └─ ConversationRuntime[sessionId]
  │    │    └─ NavigationSnapshot
  │    └─ device B → 独立 DeviceRuntime
  └─ ActiveDeviceId                         只决定当前显示
```

### 状态作用域

| 状态 | 必须携带的作用域 |
| --- | --- |
| 连接、错误、重连、凭据版本 | deviceId |
| workspace 列表 | deviceId |
| 任务双数据源与合并结果 | deviceId + workspaceId |
| conversation rows、模型/模式/思考、工具状态 | deviceId + workspaceId + sessionId |
| 草稿、待上传附件、滚动锚点、展开状态 | deviceId + workspaceId + sessionId 或显式 draftId |
| 界面主题、语言、设备列表排序 | 应用偏好；不能被某台设备协议推送无意覆盖 |

### 必须保证的行为

1. A → B → A 不主动断开 A；恢复 A 的工作区、任务、草稿、滚动锚点和展开状态。
2. A 的连接/订阅/请求失败只影响 A；B 保持可读写。
3. 同一设备连接进行中再次点击，复用同一 Future；选择 B 后 A 的晚到成功不能把界面切回 A。
4. 断连时更新真实状态并把 bridge 标记 degraded；命令等待健康恢复。健康状态下的超时不得无条件自动重发文本。
5. 重新连接先恢复 bridge、重新握手/订阅，再恢复发送能力；页面不继续使用旧 transport。
6. 快照、增量、任务 channel 数据分开保存并按来源合并；空快照不能清掉另一来源。
7. 移除/断开某台设备后，迟到响应不能把记录或连接「复活」；取消 timers、subscriptions、pending requests。
8. 凭据更新是独立操作：保留设备本地身份、替换凭据、失效旧连接，再重新验证。
9. 安卓锁屏/后台、进程被回收、Web 标签页被挂起必须区分。目标是恢复状态与增量同步，不承诺所有设备无限期后台常连。
10. 设备页只展示已知的实时状态：未连接/连接中/已连接/重连中/连接失败。最近使用不能当在线证据。

### 首批故障注入验收

- A/B 并发连接、反向完成；当前设备保持最后一次选择。
- 连接中移除 A，随后 A 握手成功；无幽灵连接、无 dispose 后通知。
- A/B 使用相同 workspaceId/sessionId；消息、草稿、模型配置不串。
- A 断网重连，B 流式输出不中断；A 恢复后只重订阅一次。
- 密文读写/密钥不可用/旧明文迁移/同设备换凭据。
- 草稿创建成功后清理原 draft key；失败保留文本；重试不重复发送。

## 5. 设备入口设计

- 首次启动：一个明确的「添加设备」入口，说明从桌面复制远程链接；表单按需打开。
- 多设备首页：窄幅内容区、设备名称、状态、最近工作区；主要视觉由黑白灰、细分隔线、克制的图标组成。
- 不展示 sid/hash，不用设备数统计卡、蓝紫色品牌块和固定底部链接输入栏占据主界面。
- 点击设备进入其最近工作区/任务，初次连接没有有效历史时才选择工作区。
- 工作界面顶部提供紧凑设备切换入口；设备管理收进该菜单。手机版避免再常驻一条设备栏挤占聊天空间。
- 平板使用官方项目/任务侧栏 + 对话布局；手机触控模式、hover/pointer 和 composer 容器宽分别验证。
- 本次交互示意只验证设备入口和状态恢复的设计意图，示例数据不连接真实桌面，不作为正式 UI 完成证据。

## 7. 实施顺序与退出条件

### M0：冻结证据与技术可行性

- 固定一次官方 Web 构建的干净资源清单、来源、SHA-256 和依赖图。
- 同数据采集手机/平板、深浅色、加载/错误/流式/弹层截图。
- 验证 Web 运行时可维护性、离线资源加载、Web origin / iframe / 存储约束。
- 单设备只读贯通后，用两个实际设备确认并行连接行为；目前只提供了一台设备入口，双设备真机验证尚缺第二台。
- 退出：记录路线选择及验证证据，确定可交付方式；不先删除 Flutter 实现。

### M1：设备核心与新入口

- DeviceRegistry、会话管理、作用域、凭据更新/迁移、取消与重连。
- 新设备入口、设备切换、最近导航、真实状态。
- 退出：多设备故障注入与真实 A/B 切换场景通过；Android release 的联网和凭据存储实测通过。

### M2：官方主要工作流程

- 项目/任务壳、完整 composer、Markdown 和行类型、历史分页、滚动、状态面板、交互响应。
- 页面按上面的能力矩阵逐项闭环，不继续堆单个 chat_page 文件。
- 退出：完整任务的开始、流式输出、工具请求、结束、离开、恢复都有可复查证据。

### M3：一致性、平台与发布

- 同视口/同数据截图差分，检查字体、间距、圆角、浮层定位和动效时间。
- 容器宽 384/576/672 周边测试；壳断点按当前官方实际值验证，不能直接继承旧版 640/720 的定制阈值。
- 手机/平板实机键盘与系统返回；失网、切网、锁屏、进程恢复。

- 退出：未完成项和偏差清单清零或明确作为产品差异接受后，才称为对应构建的对齐版本。

## 8. 对项目认知库的调整要求

当前 project-cognition 是 Zemote 的经验库，不完全描述当前仓库。它仍然有价值，但执行时必须验证：

- 不存在的 `main_shell.dart`/设置页/日志页不能当成现成能力。
- 「纯 Dart、零 Flutter 依赖」与 `conversation.dart`/`zemote_client.dart` 使用 foundation 的事实应区分为「无 Flutter UI 依赖」，不能声称可直接运行于任意 JS/原生宿主。
- 发布版本来源的文字规则存在冲突，按实际发布文件和测试统一后再维护。
- 「持续重试」与当前 15 次循环不是同一语义，未来实现必须明确失败后的恢复策略。
- 官方截图、DOM、实际 bundle 代码优先于旧文档中的推断；差异必须写清构建与日期。
